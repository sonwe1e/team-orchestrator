# 协作示例

这些示例展示职责怎样适配不同交付物；不构成固定人数、工具或技术栈要求。每次仍以用户目标、可用资源和原始材料决定实际分工。

## 例 1：性能或实验任务

**请求**：在保持结果质量的前提下，降低一套处理流水线的耗时。

- 组织者确认质量约束、现状基线、最终使用环境和验收口径。
- 方案负责人梳理流程与可改边界；研究者独立检查瓶颈证据、备选方法及反例。
- 在同一输入与条件下设计能区分瓶颈假设的小实验，再安排执行者修改。
- 为测试设备指定使用负责人或排期，避免并发负载污染比较。
- 验证者检查质量是否保持、前后条件是否一致、结果是否可复现；整合者验证完整流水线。

没有目标硬件时，可以交付分析、修改和目标环境验证步骤，但性能数字保持未验证。用户仅要求分析时，交付分析，不自动改代码。

## 例 2：数据清洗

**请求**：筛出更均匀的插帧训练样本，并保留处理记录。

- 先把“均匀”落实为用户认可的可观测指标；不要自行将时间均匀等同于运动幅度相近。
- 研究者分析指标假设与失效情形；方案负责人安排原始数据、清洗副本、样本身份和规则版本。
- 执行者按不重叠分片处理，每份交付包含输入清单、保留/剔除清单和处理原因。
- 验证者抽查边界样本、静止区域、异常输入以及前后分布；核对各分片重复或遗漏。
- 整合者合并清单和输出，确认总量与分类口径一致，保留原始数据和可追踪依据。

如果阈值会影响大量样本且用户目标尚不明确，先做可撤销的小样本分析，集中澄清取舍后再处理完整数据。

## 例 3：研究与比较报告

**请求**：比较三种方案，给出可解释的选择建议，不实现产品。

- 组织者确认用途、评价维度、资料范围和期望交付形式。
- 不同研究者按关键问题或证据来源分工，记录来源、时间、适用条件与冲突；不让每人重复做相同的全量调研。
- 方案负责人评估约束与落地成本；报告执行者将证据整合成清楚的比较。
- 验证者逐项检查关键结论与来源的支持关系、推断边界、时效和评价口径。
- 组织者交付报告和证据缺口，在报告范围内收尾。

不强行创建编码任务，不把多数研究者同意视为事实，不把报告中的下一步建议自动转成开发任务。

## 例 4：设计、培训或文档任务

**请求**：为新用户设计一份上手流程，形成可用的内容与界面说明。

- 方案负责人定义用户路径、信息层级和交付边界；研究者核对受众问题、参考证据和可能的理解障碍。
- 执行者按独立模块制作内容或设计，先统一术语、状态、输入输出与视觉约束。
- 验证者从用户目标出发检查任务是否可完成、内容是否正确、状态是否覆盖、跨模块是否一致。
- 能预览时检查真实渲染；无法渲染时区分内容检查与视觉验证，不宣称已观察用户体验。

不以主观“喜欢”替代需求与可用性依据，也不把未开展的真实用户测试写成完成。

## 例 5：清楚的小改动

**请求**：把说明中的错误参数名改正，保留其余内容。

组织者读取实际位置，完成局部修改并核对上下文即可。按风险决定是否需要独立检查；不自动建立完整研究团队或重新询问已经明确的修改意图。

## 例 6：环境不支持多 Agent

继续使用“目标 → 方案 → 执行 → 复核 → 交付”的流程，在实际能力内完成任务。明确团队职责由单 Agent 分阶段承担、没有独立 Agent 验证。

不虚构任务 ID、角色讨论、并行日志或独立背书；缺少的能力只限制相应部分，不自动中止仍能完成的工作。
