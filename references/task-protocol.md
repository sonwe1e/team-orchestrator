# 任务协议与代理调度

把职责落实为可追踪的任务、产物和交接。记录只需足够支持正确协作，不要求为每个小任务建立完整表格。

## 目录

- 1. 任务契约
- 2. Agent 与 sub-agent 的继承和再委派
- 3. 全局任务树与真实并发
- 4. 写入负责人及共享资源
- 5. 契约、接口和产物版本
- 6. 状态与交接
- 7. 适配实际工具
- 8. 失败、失联与恢复

## 1. 任务契约

每次委派都说清楚目标、输入、产物、边界、验收和回传对象；简单任务可以用一个短段落表达。依赖、资源、接口和再委派权限仅在有关时补充，但不得省略已知风险或关键约束。

```text
任务：T3；父任务：T1；契约版本：v1
负责人：实际 Agent 标识；回传给：协调者
目标：完成什么结果，如何帮助用户达成目标
输入：需要读取的文件、资料、已有结论及其版本
产物：具体文件、补丁、实验结果或带来源的结论
边界：可修改的范围、必须保留的行为、禁止扩大的范围
依赖：哪些任务或输入已就绪；不能自行假定完成的事项
验收：可观察的成功条件、必要检查和证据
资源：需独占的文件、数据、设备、端口或外部写入对象
再委派：允许的子任务范围，或本任务不得继续拆分
升级条件：何种情况暂停当前动作并联系协调者
回传：产物位置、实际变更、验证结果、证据及剩余问题
```

对于复杂任务，先复述目标并集中列出影响路线的疑问；已确认的需求保留在契约中。目标清晰且动作已获授权时直接执行，不要求用户机械地再次确认。

不能把“优化一下”“负责测试”作为完整任务。验收应针对结果，例如“清洗后每条记录可追溯到输入”，而非“调用指定函数一次”。

## 2. Agent 与 sub-agent 的继承和再委派

- 子任务继承父任务的用户目标、约束、权限、证据要求和已确认决定；权限只能相同或更窄。
- 再委派用于独立证据、不同专业能力、可分离的产物或独立验证。先说明新增价值，不复制同一任务给多人后等待投票。
- 父负责人对所有子任务的整合和完成负责，不能仅转发子代理回复就宣布交付。
- 在契约允许的范围内再委派，并向协调者登记子任务、真实 Agent 标识和资源需求。父任务明确要求组织团队或分配子代理，并已给出可用名额时，视为已授权在该边界内再委派，直接创建并登记，不重复请示。仅当再委派权限或可用名额确实不明确时，先提交拆分建议，由协调者安排，不另行向用户索取普通调度许可。
- 子任务不得另建无法被根协调者看到的任务树，也不得绕过并发上限、审批或原任务限制。
- 子代理只接收完成任务所需的上下文；必须包含相关约束和关键原始证据，不能只给上游结论。
- 如果子代理依赖尚未证实的上游判断，应标明是假设，并保留验证入口。

## 3. 全局任务树与真实并发

根协调者维护一份统一任务记录，可以使用现有任务工具、短表或项目记录。至少能回答：谁在做什么、等待什么、写哪里、产物在哪里。

| 任务 | 父任务 | 真实 Agent | 状态 | 依赖 | 写入或资源范围 | 契约版本 |
|---|---|---|---|---|---|---|
| T1 | 无 | 实际标识 | 执行中 | 无 | 整合文档 | v1 |
| T2 | T1 | 实际标识 | 待验收 | 无 | 调研记录 A | v1 |
| T3 | T1 | 未分配 | 等待依赖 | T2 的结论 | 输出副本 B | v1 |

- 启动前确认环境支持的真实并发数、当前活跃 Agent 和可用工具；遵守运行环境限制，不自行声称拥有额外槽位。
- 按实际限制统计根 Agent 和各层子代理。无空位时排队或分阶段复用角色，不让多层任务各自假定有独立配额。
- 协调者统一登记和分配槽位；多个父代理不能同时占用同一份可用额度。
- 依赖未满足的任务保持等待；可先做不依赖该结果的准备工作，但不能伪造输入。
- 同时安排具有独立价值的工作；数量服从任务可分性和质量需求，不因角色列表有六项就固定创建六个 Agent。
- 实际创建失败要更新记录并重新调度。任务已完成不代表进程或槽位必然释放，以工具提供的真实状态为准。

## 4. 写入负责人及共享资源

每个共享可变范围在同一时段只有一个写入负责人。允许多人只读审阅；并行产物应放在不同文件、数据分片或隔离工作区，指定一人负责整合。

```text
资源：服务器 S 的 GPU 0–3 / 输出目录 results/run-17 / 端口 8123
持有人：T4，实际 Agent 标识
用途：运行候选方案；输入数据只读
占用条件：启动前确认无冲突；预估时长只用于安排检查
释放证据：相关进程已结束，输出已落盘，负责人确认可交接
```

- 资源包括文件区域、共享数据、GPU、CPU 密集实验、端口、数据库表和外部应用中的写入对象。
- 不仅检查文件冲突，还检查实验干扰：并行负载可能影响性能测量时，隔离资源或串行测量。
- 对同一文件无法可靠隔离时串行修改。使用工作树或副本只能解决相应隔离范围内的问题，不能视为远程设备已隔离。
- 协调者的登记是一项协作约定；只有实际工具提供时才能声称存在强制锁定。
- 预约时间过期、Agent 无回复或任务状态变化，都不能自动证明资源已释放。

## 5. 契约、接口和产物版本

改变目标、接口、输入或验收标准前，检查是否影响其他任务。协调者更新相应版本，并通知所有受影响的负责人。

```text
变更：T2 契约 v1 → v2；原因：已确认输入字段定义不同
影响：T3 的字段映射和对应检查；未影响的任务继续
动作：暂停旧映射的写入，读取新版定义，确认后恢复
失效证据：基于旧字段的检查结果不能支持新版结论
```

- 任务交接必须注明所用契约、输入和产物版本；可采用提交号、文件摘要或明确快照标识，不虚构标识。
- 相关输入或产物变化后，旧验证结论标为不再适用，只重做受影响的检查。
- 发出消息不等于对方已收到。对影响写入正确性的变更，收到确认或实际停止旧任务后才能交接；可用时调用中断工具。
- 小修正不必重开整个讨论。目标或验收改变必须有依据，不能为掩盖失败而降低标准。

## 6. 状态与交接

采用能够区分“写完”和“验收通过”的状态：待分配、等待依赖、执行中、待验收、返修中、已验收、受阻、已取消。

- 待分配或等待依赖：指定负责人，确认输入和资源就绪后进入执行中。
- 执行中或返修中：形成完整产物并完成必要自检后进入待验收。
- 待验收：按预定标准通过验证才进入已验收，并注明是否独立；必要的独立验证未能执行时保持待验收或受阻。局部缺陷进入返修中；关键假设失败则回到设计并更新契约。
- 受阻：记录缺少的条件、已完成部分和恢复条件；不等同于通过，也不等同于放弃整个目标。
- 已取消：停止相关动作并交回资源；保留已有有效证据，不删除其他人的工作。

```text
交接：T3，契约 v2；产物：具体路径与实际版本
已完成：用户现在可以获得什么结果
实际修改或处理：范围及关键差异
验证：通过 / 未通过 / 未执行；条件、方法与证据位置
遗留问题：影响、严重程度、复现或确认方法
接收方下一步：验证哪些结果，或继续哪个依赖任务
资源状态：哪些已释放，哪些进程仍在运行及其真实标识
```

接收方核对产物可访问、版本相符、依赖充分后确认交接。仅回复“完成了”“应该没问题”不构成交付证据。

## 7. 适配实际工具

- 根据环境实际提供的工具完成创建、通信、等待、中断和状态查询，不写死不存在的 API，也不宣称工具未支持的隔离或重试能力。
- 工具存在但不可用时，记录具体限制，继续可完成的部分；必要时将任务改为顺序执行。
- 无多 Agent 工具时，由同一 Agent 分阶段承担职责并保留记录；明确这是顺序自检，不能称为真实并行或独立审查。
- 缺少运行环境或数据时可做静态检查、设计审查或可复现实验方案，但必须明确实际没有执行的验证。

## 8. 失败、失联与恢复

失联先查询工具状态、进程和已有产物；不要立即创建替代 Agent 写入同一范围。中断 Agent 也未必终止其启动的外部作业，须分别确认。

确认旧执行已停止并收回资源后，才将该范围交给新负责人；不能确认时，替代任务只读诊断，或使用完全隔离的输出与资源。

从已保存的任务契约、有效产物和检查点恢复。不能可靠判断某次外部写入是否成功时，先读回状态，避免重复提交；旧 Agent 恢复后也不得自动重新获得写权限。

修复应带来新证据。重复失败而没有新增信息时，调整诊断方法或升级关键假设；不要无限重试，不覆盖用户或其他 Agent 的未交接变更。
